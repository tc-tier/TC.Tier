ApplyPipeline

提交→应用管道（spec-05 §3 定案）——与共识循环解耦的独立单 worker：

  • 按 index 序取 committed 批次 [lastApplied+1, commitIndex] → ApplyAsync 逐条（严格与日志序一致）；
  • appliedIndex 节流落盘（spec-05 §2——每 N 条/每 T 毫秒，断电损失 ≤ 节流窗口重放成本）；
  • 配置条目分流（spec-04——配置切换 = apply 产物，经回调通知状态机；判别 = 条目结构字段 Kind（RaftEntryKind——wire v3 信封之死））；
  • 应用完成 → AppliedTo 事件（状态机完成 ReplicateAsync pending——spec-05 契约②）。

★ 正确性（spec-05 §3）：raft 安全性 = 多数派提交，与本地 apply 无关——apply 落后安全 （只延迟读服务，不产生错误状态）；单消费者 FIFO 保序 → 按序恰好一次（重复仅发生在重启重放—— at-least-once 契约，业务幂等）。

★ 存储经 IRaftStore 端口（spec-12 §8.1）：★ 双源读（spec-03 §7）—— applied < N₀ 的跨界区间由 RebuildCoordinator 经快照读面补齐（快照 = 可导出的日志前缀镜像），管道无需感知快照面。

ClusterConfig

★ 稳定序列化（Serialize()——配置条目 payload 格式）：配置变更经日志复制 跨节点传播、重启经快照/重放恢复——格式必须稳定。

★ 数据面归 Fs（裁定③——镜像/迁移通道归 Fs 既有能力）；本面只做时序调度 + 配置变更——日志复制追平是缺省搬迁形态，镜像通道由装配方在入组前预热（接口不变）。

RaftGroupChannel

RaftGroupHost

RaftRpc

Raft RPC 消息族（spec-01..05 消息语义 × spec-12 §6/§10——[WireMessage] 声明即线格式； RPC 族走请求回调形态：RpcId 取消——CorrId 由传输承载，消息族不携带（spec-12 §6 形态映射）。

★ 线格式（生成物：[Tag 1B][Term 8B 公共前缀][子类字段声明序]，全部小端；NodeId = 16B 不透明字节串原序嵌套件）：tag 沿用类型码 0x01-0x08（PreVoteReq…InstallSnapshotResp）。 ★ 线格式 v3（信封之死——序列化 v3，件 B 配置 v2 先例）：AppendEntries 条目区由 [Terms 表][Payloads 表]（v2，载荷 = 引擎信封）改为 EntriesRegion 单 blob（区内 [Count 4B][×N: RaftAppendEntryHeader 13B + Content]—— kind 升格条目结构字段，存储直写单拷贝）。内部协议未发布，无跨版本共存。

★ 无响应超时重发机制（raft RPC 幂等——丢失由心跳/选举定时器自然补偿；请求回调 缺省 at-most-once 投递语义与此天然对齐）。

★ 降级统一规则（spec-01 §3.2）：任何状态收到更高 term 的 RPC → 先落盘再应答； 应答恒回带 Term（应答方 currentTerm——对端据此发现自己落后）。

★ 解码防御：未知 tag / 截断 / Count 超上限 = false（畸形报文丢弃）；已知 tag 尾部 扩展字节容忍（前向兼容）。条目表防御上限 MaxEntriesPerAppend（旧手写 codec 只查负数——生成化补齐截断防御）。

RaftStateMachine

Raft 状态机（spec-01 全量——状态集合/转换/任期语义/选举含 PreVote/超时随机化/事件循环骨架； spec-02 follower 侧——AppendEntries 应用与 commitIndex 推进；spec-12 §6 形态映射——RPC 族走 请求回调（CorrId 传输承载、at-most-once 缺省 + raft 定时器自愈）。

★ Actor 形态（spec-01 §6.2）：单 worker 循环——取事件 → await handler → 取下一事件； 同一时刻一个状态转换在处理（状态机串行化 + 存储端口单写者契约天然满足）。 handler 只做快路径（状态判定 + 本地持久化 await）；网络应答/定时器 = 新事件入队或请求任务回投， handler 从不 await 网络应答。

★ 挂载（spec-12 §3.5）：StartAsync 经 TC.Tier.Core.Net.Channels.ICoreProtocolPort 内部口注册 Raft（0x01）请求 handler——与使用方协议域同一分发路径（机制零特权）； 传输端点生命周期归装配层。

★ 复制发送已出循环（spec-10 D1）：Leader 侧 AppendEntries 发送/应答处理/心跳在 ReplicationProcess per-peer 续体链（peer 间并行）；commit 推进经 TC.Tier.Core.Net.Raft.RaftStateMachine.AdvanceCommit(System.Int64) 并发单调化回投本机。

★ 定时器（spec-01 §6.3）：每状态至多一个活动定时器——循环按最近截止 await（选举超时/ 心跳），到期入队对应事件；每次触发后重掷随机超时（spec-01 §4.1 规则 4）。

★ 降级统一规则（spec-01 §3.2）：任何状态收到更高 term 的 RPC → 先落盘（term, votedFor=∅） → 再应答/转换；应答恒回带 currentTerm。

★ 持久化经 IRaftStore 端口（spec-12 §8.1——条目 = (Term, Kind, Content) 三元组（wire v3 信封之死——kind 结构字段），双水位模型：追加即分配 + WaitForPersistedAsync(long, CancellationToken) 应答前同步点）。

ReplicationPolicy

复制策略（spec-02 复制层配置化——条数/字节/时间三维度任一触发一次 AppendEntries 批量发送）。

★ 默认全零 = 立即推送（append 即通知发送、窗口 1 流水线）。

★ 三维度语义：

- BatchSize：单次 AppendEntries 批上限（条数维度，默认 1000——spec-02 §2 攒批形态）

- BatchWindow：攒批时间窗口（时间维度——窗口内到达的 append 合并为一次发送； 0 = 立即推。真实网络下摊销 RTT 的关键参数；进程内场景收益小）

- MaxBatchBytes：批字节上限（字节维度；0 = 不限）

★ 窗口判定粒度 = 状态机 tick（5ms）——窗口配置自由，到期误差 ≤ tick 周期。

ReplicationProcess

复制引擎（spec-02 Leader 侧全量）——nextIndex/matchIndex 管理、AppendEntries 构造与应答处理、 冲突回退（hint 加速）、commitIndex 推进（Figure 8 约束）、心跳循环。

★ per-peer 续体链（spec-10 D1）：复制发送从共识循环线程抽出，每 peer 一条独立续体链 （线程池续体——不占专属线程，peer 间并行：发 A 时可处理 B 的 ack）；peer 状态 （nextIndex/matchIndex/在途）只被本链读写（raft 本要求每 peer 单在途 AppendEntries—— 串行是协议本性，单写者零锁）。信号驱动：新条目（NotifyAppended(int, long)）/ 应答投槽（HandleRespAsync(NodeId, AppendEntriesResp, CancellationToken)）/ 心跳 tick（HandleTick()）→ lane 唤醒 → 消费应答槽 → 发送判定（滞后 / 心跳到期 / 在途超时重试）→ 回挂等待。

★ 请求回调形态（spec-12 §6）：发送 = 出站请求任务（per-call 超时对齐在途重试窗—— 应答由传输 CorrId 配对）；应答到达经 TC.Tier.Core.Net.Raft.ReplicationProcess._onRespArrived 路由（状态机 term/ReadIndex 前处理）→ HandleRespAsync(NodeId, AppendEntriesResp, CancellationToken) 投槽/直跑——lane 单写者不变式与旧事件面同构。

★ 快照判定：nextIndex ≤ 本地快照覆盖点 → 经 TC.Tier.Core.Net.Raft.ReplicationProcess._onSnapshotNeeded 通知状态机 改走快照安装（spec-03 §2 触发条件——增量复制无法接续）。

★ 时序（spec-03 §2）：leader 先导出（开流 → 逐条帧写 → End）→ 再发 InstallSnapshotReq 握手；★ follower 在 acceptor 回调即启动消费循环边收边导（流式背压契约：读端不读 = 写端挂起——IStreamAcceptor"重活自起消费循环"），ImportSnapshotAsync(NodeId, SnapshotCoordination?, CancellationToken) 等待导入完成 （"快照已经注入传输面送达，本 RPC 只做同步点握手"语义）。

★ 挂载：StartAsync 经 TC.Tier.Core.Net.Channels.ICoreProtocolPort 内部口注册 0x04 acceptor。 每 peer 至多一个在途导入（引擎快照安装防重入保证）。

★ 流式纪律：导出/导入均逐帧 O(单帧) 驻留（GB 级快照不驻内存）。

SnapshotSwarmBlockSource

快照块源（spec-12 §6.1 装配——ISwarmBlockSource 的 holder 侧实现： 按内容标识 + 块号从物化内容做几何切片）。

★ 内容知识归使用方（快照安装装配）——本件只认 SnapshotSwarmContent 的字节流，几何定位（块偏移 = 块号 × 块大小，末块截短）由 SwarmManifest 承载。

★ 单 manifest 源（与 SetSource(ISwarmBlockSource?) 单槽语义对齐——一次发布一个 快照；多快照并存的 holder 后续按需扩多 manifest 源）。

SnapshotSwarmContent

块化快照内容（manifest + 物化字节流——holder 侧随机块访问的缓存）。

SnapshotSwarmSync

快照多源同步装配（spec-12 §6.1 消费者——SwarmSync 首消费件）：把快照条目流块化 （SnapshotBlockizer）后走多源并行拉取；与单源流式路径 （SnapshotStreamTransfer）共享同一存储端口（IRaftStore 快照读/导入面）， 产物（目标快照区）逐字节一致——对拍契约见测试。

★ 角色对称（spec-12 §4 对称节点）：每节点既可作为 holder（PublishSnapshotAsync(long, int, CancellationToken) 发布块化内容供拉取）也可作为下载方（InstallSnapshotAsync(SwarmManifest, IReadOnlyList<NodeId>, Action<long, NodeId>?, CancellationToken) 多源拉取重装导入）； holder 列表与 manifest 的交换是装配/握手面（InstallSnapshot RPC 携带——归 T6 引擎接线）， 本件只提供机制（发布 → 取 manifest；收到 manifest + holders → 安装）。

★ 下载侧重装 O(快照字节) 缓冲（无序块按几何偏移落位后顺序解析导入——导入面仍逐条流式消费）； 传输线经 SwarmSync 逐块流式（O(块) 驻留）。

SnapshotSwarmTransfer

快照多源传输（spec-12 §6.1 × spec-03 §2——ISnapshotTransfer 的 swarm 数据面实现： 导出 = 块化当前快照发布供拉取 + 握手协调数据（manifest + holders）；导入 = 按握手面 收到的协调数据多源拉取重装导入 + 完成后向 source 上报持有（多源从字面成立））。

★ 时序（与单源同构）：leader 先导出（发布块源）→ 再发 InstallSnapshotReq 握手 （manifest+holders 随 RPC）→ follower 多源拉取导入 → 应答；产物与单源流式路径逐字节 一致（对拍契约见测试）。

★ 持有者表：leader 导出 = 换代 ResetHolders(SwarmContentDomain, Opaque16)（清表+登记本端）→ Holders = GetHolders(SwarmContentDomain, Opaque16)（含本端兜底）；follower 导入完成 = Announce 上报（spec-12 §6.1 增量——多源候选由持有表供给，块内容寻址 + CRC32C 校验保证任意 持有者副本等价）。

TransferLeaderReq

领导权定向转让（二期-D2——leader → 目标的 TimeoutNow：目标跳过预票立即发起 真选举；根 Term 供目标核对在位权威）。

TransferLeaderResp

领导权转让应答（Accepted = 目标已受理并发起选举——诊断面，调用方经换届观察完成）。

WitnessHighWaterStore

Witness 高水位存储（二期-F2——DDR-F2）：witness 节点的 IRaftStore 形态。

★ 只持久化「日志存在性证明」——高水位对 (LastIndex, LastTerm) + (Term, VotedFor) 选举契约；日志体/状态机/快照全部缺席（witness 永不成为 leader，故永不提供日志体， 永不导出/安装快照——无体日志不会被读取）。

★ 本实现为内存版（测试/嵌入式/内存形态）；生产持久化（高水位断电丢失 = 退回 旧高水位，投票保守方向安全但可能阻塞当选——建议装配方 fsync 持久化）归装配方按 本接口封装。

Interfaces

IApplySink

提交 → 应用管道接口（spec-05 契约——共识循环与 apply 解耦）。

状态机（共识循环单 worker）commitIndex 推进 → Submit(long) 投递 committed 批次； apply 管道（独立单 worker）按序 apply → 经 AppliedTo 通知状态机 （完成 ReplicateAsync 的 pending——spec-05 契约②：返回 = committed 且 applied）。

IRaftStore

raft 引擎对持久化的全部需求面（spec-12 §8.1——从引擎消费面提取的端口；实现 = 适配器（组装层 TierWAL）/ 夹具（测试项目 InMemoryRaftStore·FsRaftStore）。 Core.Net 零存储自有——数据持久化端口唯一。

★ 条目 = (Term, Kind, Content) 三元组（wire v3——kind 升格结构字段，信封格式消灭； Kind 取值 RaftEntryKind）——日志帧格式知识归适配器（引擎与存储互不泄露布局）。

★ 双水位模型：AllocatedIndex = 追加即分配（含未持久化窗口）； PersistedIndex = 已持久化尾（WaitForPersistedAsync(long, CancellationToken) 推进——fsync 时机由协议层控制， 应答前同步点）。

★ 不变量：term 单调不降；AppendAsync(long, IReadOnlyList<(long Term, byte Kind, ReadOnlyMemory<byte> Content)>, CancellationToken) 的 prevIndex 为前置断言 （冲突回退一体——prevIndex < 当前尾 = 截断后重写）；快照区（≤ SnapshotIndex）不可回写。

IRebuildableApplySink

可重建 apply 管道标记（spec-03——follower 快照安装后重建业务状态：导入 → 重放快照帧流 → appliedIndex 重置到 N₀ → 增量接管）。ApplyPipeline 实现。

ISnapshotTransfer

快照传输协调器（spec-03 §7——协议层实现网络版传输面注入存储：导出/导入经注入面开会话； 目标绑定 = 装配层内部细节——每 follower 一次调用 = 一个新会话）。

★ 装配（Builder/测试组合根）实现：设置当前目标（写/读会话路由）→ 调存储适配器 ExportSnapshotAsync/ImportSnapshotAsync。状态机只依赖本接口——传输形态零耦合。

★ 握手协调面（spec-12 §6.1）：导出返回 SnapshotCoordination（swarm 形态 的 manifest+holders——由状态机装入 InstallSnapshot RPC 握手面随行）；null = 单源流式形态 （数据面自带一切，RPC 协调字段零值）。导入对称消费协调数据。两形态不可混装（集群装配 一致——swarm 导入方收到 null 协调数据 = 装配错误快速失败）。

IStateMachine

业务状态机接口（spec-05 §1 定案）——日志即状态机：业务状态 = 已提交日志前缀的确定性函数；重建 = 重放。

★ 业务方唯一必须实现 ApplyAsync(long, ReadOnlyMemory<byte>, CancellationToken)（按序应用已提交命令——index 单调递增、与日志序一致； 只被 ApplyPipeline 单 worker 调用——业务存储无并发写，结构层积木直接可用）。

★ at-least-once 契约：apply 可能重复（断电重放 appliedIndex 之后区间）——实现须幂等/容忍重复 （raft 标准语义；at-most-once 会话去重归用户面 spec-08）。

★ ExportStateAsync(IAsyncTransferWriter, CancellationToken)/ImportStateAsync(IAsyncTransferReader, CancellationToken) = 可选优化路径（业务状态导出/导入， 冷启动免全量重放——存储与传输由使用方自理，协议层零绑定）；不使用不阻塞任何正确性。
