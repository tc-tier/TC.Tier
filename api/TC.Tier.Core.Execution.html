AsyncPump

单线程异步泵（执行原语——调用线程驱动异步状态机）：work 执行期间安装专用 SynchronizationContext，不写 ConfigureAwait(false) 的 await 续体经 Post 回泵队列、由同一线程逐项执行——单线程亲和（work 状态机无需锁/原子，泵线程是唯一推进者）， 零额外线程、零跨线程唤醒（对照 SyncAsyncBridge：桥=独立池+等待者 park，泵=就地推进）。

★ 上下文契约：泵域内续体回流是功能——消费方在 work 内不写 ConfigureAwait(false) （与全仓 ConfigureAwait(false) 纪律的边界：域外它是防 UI 上下文捕获的缺省姿态，域内回流即语义）。 第三方库内部的 ConfigureAwait(false) 段不回流（线程池执行）——泵空转等待其完成，语义安全。

★ 死锁拆解：Run 内再 Run = 同线程等自己泵（自锁）——快速失败；work 内禁止阻塞等待 （协作式异步契约——阻塞占死唯一泵线程，域内续体无人推进）；跨 await 持有的锁需依赖单线程亲和 化解（这正是本原语的存在理由），跨线程进入域外等待是调用方责任。

★ 空转等待：work 等待不回流的段（外部异步/第三方 ConfigureAwait(false)）时队列空—— park 在事件上（Post/任务完成双双唤醒），不自旋不烧 CPU。

BackgroundWorkerLoop

通用长生命周期后台循环骨架（第一层——循环骨架，无队列）。与业务无关。

★ 封装：执行器（注入 TaskScheduler（如 IsolatedTaskScheduler.Shared）或 null=公共池 + ConsumerCount 多消费者扇出——消费者是协作跑在调度器线程上的循环 Task，不是线程数）+ 幂等启停 + 超时等待退出 + CAS 防双 Dispose + 单周期异常隔离。

★ 子类实现 RunOneCycleAsync(CancellationToken)（一个工作周期）+ 信号源选择（见 worker-loop-unified-design.md §5）。

★ 自身 IDisposable——LifecycleBase<THints> 内建持有时， Dispose 统一编排 Stop + WaitForExit（见 worker-loop-unified-design.md §4）。

★ 多消费者：ConsumerCount 个执行体共跑同一循环（各自 RunOneCycleAsync(CancellationToken)）， 常用于事件驱动队列的多消费者 drain（BackgroundWorkerLoop<T> 内建优先级队列 + counting-semaphore 逐项公平唤醒，见 BucketPriorityQueue<TPriority, T>）。默认 1 = 向后兼容。

BackgroundWorkerLoop<T>

事件驱动 + 队列的后台循环骨架（第二层——内建 5 档优先级队列）。

★ 继承 BackgroundWorkerLoop（循环骨架 + 启停 Dispose + 多消费者），追加： 内建 BucketPriorityQueue<TPriority, T> + 统一 Enqueue(T, WorkerPriority) 入队 + abstract ProcessItemAsync(T, CancellationToken) + virtual RunOneCycleAsync(CancellationToken)（出队分发）。

★ 开箱即用（标准后台任务模式）：子类只实现 ProcessItemAsync(T, CancellationToken)， 基类默认 RunOneCycleAsync(CancellationToken) 从队列出队分发。入队统一 Enqueue(T, WorkerPriority)。

★ 多消费者：构造传 consumerCount > 1，N 个消费者共 drain 同一优先级队列（counting-semaphore 逐项公平唤醒，见 DequeueAsync(CancellationToken)）。

★ 需要重写：子类 override RunOneCycleAsync(CancellationToken) 自定义循环逻辑 （如 Lifecycle 的 fire-and-forget 并发内核）。内建队列仍在。

CpuSampler

通用 CPU 利用率采样 + 限流系数计算（Core/Shared）。继承 BackgroundWorkerLoop—— PeriodicTimer 驱动采样，Start/Stop/Dispose 全由基类。

★ 计算模型（明确，不靠概念）：采样本进程 CPU—— raw = ΔProcess.TotalProcessorTime / (Δ实际墙钟 × ProcessorCount)，归一化 0~1 （1.0 = 本进程跑满所有核）。是进程口径而非整机口径：其它进程造成的系统饱和本采样器看不见 （整机口径需性能计数器，跨平台不可用，故明确取进程口径）。

★ 平滑：EMA——ema' = α·raw + (1−α)·ema，首样本标志位初始化（不拿 ema==0 当哨兵： 旧实现空闲→高载第一个样本直接跳变，无平滑——"不平稳过渡"的根因）。

★ 限流系数 ThrottleFactor：分段线性——CPU ≤ lowCutoff → 0（不限流）； lowCutoff~highCutoff → 线性 0→1（软降速）；≥ highCutoff → 1（强阻塞）。 系数计算是纯函数（TC.Tier.Core.Execution.CpuSampler.MapThrottleFactor(System.Double,System.Double,System.Double)，internal 可测）。

★ Hub 折叠：注入 ObservabilityHub 后每采样发布 cpu.utilization / cpu.throttle_factor Gauge，档位切换（正常→限流→强阻塞→恢复）打日志—— 限流判断进可观测视图，不再隐形。

★ 热路径零开销：读 CpuUtilization / ThrottleFactor 走 Volatile.Read； Hub 未注入（默认 Disabled）时指标短路零开销。

DeadlineRegistry

时间驱动唤醒注册表（零 TimerQueue 依赖原语——拉取模型，设计稿 docs/design/tc-tier-net-timerqueue-free-tick-pacer-design.md）。

★ 背景判例：.NET 8 TimerQueue 在高频触发窗口把 PeriodicTimer 从定时器链表弄丢 （堆转储实锤：TimerQueueTimer _next=0,_prev=0 孤儿）——tick 永不再来 → 共识循环冻结。 本原语用专用线程 + WaitHandle.WaitOne 同步等待（futex 实现）取代一切定时器依赖。

★ 拉取模型：条目不存 deadline 值——持 Func<long>（deadline 计算委托， owner 侧读自己的 Interlocked 字段，TickCount64 单位）+ Action（唤醒回调）。节拍线程 每轮醒来重扫全部条目：到期者回调、未到期者取最早值睡眠。零更新竞态、无堆、无重排协议； deadline 早移由封顶（TC.Tier.Core.Execution.DeadlineRegistry.DefaultCapMilliseconds=100ms）保证有界晚醒。

★ 分片：DeadlineRegistry——每 shard 独立条目表 + 独立 节拍线程（懒启：首个订阅才起、起后常驻）；订阅按 round-robin 稳定分配，条目终身不动 （句柄持 shard 引用——退订零查找）。扫描成本 = 条目数 × 唤醒率：单分片到 10⁴ 级无感， 万级 → shard=2、10⁶ 级 → 4（升级触发器见设计稿 §3.2）。

★ 生命周期：IDisposable/IAsyncDisposable——CAS 防双释放 + 有界等节拍线程退出（对齐 BackgroundWorkerLoop 样板）。Shared 进程级懒加载单例（IsolatedTaskScheduler.Shared 同款先例）。

IsolatedTaskScheduler

隔离线程 TaskScheduler——在 M 个私有线程上执行任务，与公共线程池（Default）完全隔离。

★ 用途：高频 / 关键路径的 worker（如引擎建段 worker）需要线程隔离——其异步 continuation 不与公共池上的 其它任务（写者、其它池工作）争抢池线程，避免饥饿/抖动。

★ 真·异步友好：任务在私有线程上执行时 TaskScheduler.Current = 本调度器，任务内 await 的 continuation 自动回到本调度器的私有线程（不经公共池）——既得「专用线程」隔离，又无 GetAwaiter().GetResult() sync-over-async（高频路径禁区）。

★ 阻塞等待模型：私有线程在 BlockingCollection<T> 上阻塞等任务（空闲不占 CPU）。

★ 稀缺资源·受控创建：每实例开 M 个真实 OS 线程（栈 ~1MB/线程）。禁止直接 new——ctor 为 internal，经 Shared（进程级全局单例）或 Create(IsolatedSchedulerOptions?)（工厂 + 防扩散护栏）获取， 使用指南见 §2（使用指南：docs/dedicated-task-scheduler.md，文档站）（选型/旋钮/注意事项/故障排查）。

★ 释放：调用方须在所有任务结束后（worker 的 WaitForExit 之后）调 Dispose()—— CompleteAdding() + Join 线程。

SyncAsyncBridge

同步-异步桥（docs/sync-async-bridge.md §6）——"写路径必须同步转异步"的统一出口。

★ Start(Func<CancellationToken, ValueTask>, SyncBridgeOptions?, CancellationToken)：在独立池上发起异步工作，立即返回 AsyncOperation 状态句柄 （返回时状态已同步置 Running——可见性原则）。调用方继续本地逻辑，最后时刻才 Wait（"Start 早、Wait 晚"）。

★ Run(Func<CancellationToken, ValueTask>, SyncBridgeOptions?, CancellationToken)/Run<T>(Func<CancellationToken, ValueTask<T>>, SyncBridgeOptions?, CancellationToken)：一次性便捷入口（Start + 有界 Wait + 失败重抛）—— 同步 API 桥接的常规形态，替代裸 GetAwaiter().GetResult()。

★ 死锁拆解：异步工作跑 DefaultScheduler（IsolatedTaskScheduler 私有线程， continuation 回流私有线程）——推进不依赖公共池可用性；同步等待者 park 在事件上（非 Task.Wait）， 无同步上下文回流、无完成边缘内联续体语义模糊。

★ 再入防护：桥 work 体内再经同一池同步等待 = 池自锁（M 线程全 park 等嵌套 work）→ Start(Func<CancellationToken, ValueTask>, SyncBridgeOptions?, CancellationToken) 快速失败（InvalidOperationException）。嵌套场景注入独立 Scheduler 分池豁免； 跨池嵌套等待必须无环（DAG，对齐 WaitForDependenciesAsync 纪律）。

★ work 契约：协作式异步——await 让出、不阻塞（M 很小，阻塞任务直接饿死同池操作， 对齐 dedicated-task-scheduler.md §7.2 教训）。真正无法异步化的同步重 IO 由调用方注入 own 单线程实例。

TaskSink

任务沉池（fire-and-forget 派发原语——执行载体 taxonomy 终态：短频繁·可丢失自愈）。

★ 契约一句话：提交即放手（void 不返回，调用方零仪式）。保证——异常收口不外泄 （计数 + 日志 + onFaulted 回调）、组生命周期（Dispose = 取消传播 + 有界 drain）；不保证——执行（已释放即拒/池拒绝/进程终）、完成通知（丢弃静默， 仅计数器事后可观测）、顺序（提交序 ≠ 执行序）。

★ 越界即错：按身份去重/单任务取消/等待指定任务完成不是本原语的语义——协议层自持状态； 长稳定异步循环走专用线程 + AsyncPump 泵域；时间驱动唤醒走 DeadlineRegistry。

★ 在途跟踪 = 原子计数 + drain 信号（提交热路径零堆分配——DisposeAsync() 等计数归零）。

TimeProviderExtensions

TimeProvider 扩展——时钟缝（故障注入面补全设计 件一）消费侧统一供给源。

★ GetMsTimestamp(TimeProvider)：毫秒单调戳——语义与存量 Environment.TickCount64 域逐字节对齐 （System 快路径直读 TickCount64；假钟按 TimestampFrequency 换算）， 落点改造零算术变更（deadline 字段全部保持 ms 域）。

★ Delay(TimeProvider, TimeSpan, CancellationToken)：provider 可注入的任务延迟—— 假钟下由测试快进驱动（零真实睡等），System 下直通 Delay(TimeSpan, CancellationToken) （缺省零变化）。
