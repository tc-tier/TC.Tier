## 0. 2026-08-17 压测发现与修复（先读这节）

本次全功能压测（并发吞吐 / 积压敏感性 / 并发正确性 / 真实负载维度）发现并修复/确认了七个问题：

| # | 发现 | 类型 | 状态 |
|---|------|------|------|
| 1 | **Async 尾插不建高层索引**：`Enqueue` 高层链接跳过 `succs==null`（尾插）——持续尾插负载（如单一最大优先级段）下高层索引永不建立，Find 退化 level-0 线性扫描（256K 积压实测 ≥1.9 ms/op） | 性能缺陷 | ✅ 已修复——尾插也 CAS 链接 |
| 2 | **Async 发布后普通写可覆盖 Marker**：`node.Forward[i] = succs[i]` 在 level-0 发布之后执行，可把并发删除者放的 Marker 抹掉——已删节点"复活" | 协议缺陷（修复 #1 后暴露） | ✅ 已修复——发布纪律：全部字段在发布前写完 |
| 3 | **Async 标记 CAS 可被 Find 的 helping splice 打败**：同字段竞态留下"F0 已标（已出队）但高层未标"的悬挂僵尸 → 后续 Enqueue 的 preds 落在僵尸旧世界（发布 CAS 恒失败）+ 队头已标无人摘 → **全体自旋的活性死锁**（DEBUG 链校验器不报警——结构不断裂） | **并发缺陷（活性死锁）** | ✅ 已修复——标记重试到 Marker 落地 |
| 4 | ~~SkipList 多消费者活性坍塌（算法特征）~~ → **实为写法缺陷 #PERF-004，已修复**（2026-08-18，commit 89014d98）：删除只校验 level-0 → marked 节点滞留高层 → Find 扫 marked 前缀正反馈膨胀（2P+2C 前缀涨至 2 万+）→ O(n) 退化至零吞吐。修复（全层级校验 + ThreadStatic 缓冲 + 内联 level-0 边）后 2T 4.3 Mops/s、MPMC 287×、正确性 16/16——**档案与误诊教训见 §4** | 写法缺陷 | ✅ 已修复 |
| 5 | **SkipList（修复后）落后大锁基线 3~4×**：8 线程 9.4 vs 32.0 Mops/s、单线程 466 vs 305ns、分配 92 vs ~0 B——细粒度锁的"区间并行"在优先队列负载下收益趋零，validate 重试仍是纯浪费功（§2/§4.3）。健康可用但吞吐定位让位于大锁 | 选型结论 | 📋 选型表已更新 |
| 6 | **大锁的柱塞放大**（§5.2 毒丸实验）：持锁者被延迟 2ms（模拟抢占/GC/页错误）→ 其他线程 op max **140ms（放大 94 倍）**；同剂量延迟在锁外仅 1.5ms。大锁吞吐王座的适用条件 = 临界区短 **且** 持锁者不被外部长延迟 | 选型边界 | 📋 已量化 |
| 7 | **无锁 ≠ 低尾延迟**（§5.1/§5.2）：Async 对持锁者延迟结构性免疫（别人的延迟不通过锁传播），但 1.3~1.8KB/op 分配率在 Workstation GC 下制造 45~186ms 的 GC 尾巴——比它免疫的柱塞还大。兑现无锁延迟确定性需 Server GC 或降分配（B' 路线） | 选型边界 | 📋 已量化 |

取证与修复全程（dump 走链 / dotnet-stack / DEBUG 示波器断言三重证据）：[../lab/async-priority-queue-root-cause.md](../lab/async-priority-queue-root-cause.md) §8。

## 1. 单线程混合往返（稳态积压 1024，均匀 8 级优先级）

### 1.1 修复前（Linux BDN，2026-08-17 上午——历史基线）

| 实现 | Mean | Ratio | 分配/次 |
|------|-----:|------:|--------:|
| .NET 内置 `PriorityQueue`（非线程安全，参照） | 14.1 ns | 1.00 | 0 B |
| `BucketPriorityQueue`（离散 8 桶） | 66.2 ns | 4.69 | 48 B |
| `SkipListPriorityQueue`（任意 long） | 515.2 ns | 36.5 | 1376 B |
| `AsyncPriorityQueue`（无锁 Route A） | 1155.8 ns | 81.9 | 1256 B |

### 1.2 修复后（Windows BDN short，2026-08-17 下午）

| 实现 | Mean | Ratio | 分配/次 |
|------|-----:|------:|--------:|
| .NET 内置 `PriorityQueue`（非线程安全，参照） | **11.0 ns** | 1.00 | 0 B |
| `BucketPriorityQueue`（离散 8 桶） | **52.4 ns** | 4.75 | 48 B |
| `AsyncPriorityQueue`（无锁 Route A，**含尾插修复**） | **423.2 ns** | 38.4 | 1256 B |
| `SkipListPriorityQueue`（任意 long） | 328.0 ns | 29.8 | 1376 B |

> **修复 #1（尾插链接）的效果直接可见**：Async 从 1155.8 ns（旧基线，82×）降到 423 ns（38×）——
> 旧实现里 1024 积压的高层索引已部分退化（最大优先级段全在 level-0），修复后索引健康、Find 走真正的跳表。
> 跨机对照仅看量级：修复后 Async 单线程已与 SkipList 同档（328~423 ns），**不再是"82 倍税"**。

### 解读

- **Bucket 仍是并发队列里的性能之王**：50~66 ns 对积压深度不敏感（出队扫桶 O(桶数)）——**优先级能映射为
  少量离散枚举时无条件选它**。48 B/次分配来自 `ConcurrentQueue` 分段（摊销）。
- SkipList / Async 的差距是"任意优先级 + 线程安全"的代价：节点式结构分配（1.3 KB/次）与锁/无锁协议开销。
  两者定位是**优先级必须任意取值**时的选择，不是速度选择。
- 与内置的 11~14 ns 对照不是"落后"，是线程安全的定价——单线程场景就该用内置（陷阱 §6 of priority-queues.md）。

## 2. 并发吞吐矩阵（混合往返 × 线程数，独立计时探针）

**方法论**：Thread 直起 + Barrier 对齐起跑 + Stopwatch 总时/总 ops；先探测轮（50K ops/线程，10s 护栏）再 5 轮正式（200K/线程，60s 护栏）取中位。BDN Parallel 组在本机高度不确定，故独立程序（`--pq-probe`）。
**LockedHeap 对照基线**（2026-08-17 追加）：一把 `lock` + 内置 `PriorityQueue`（四叉堆）+ Bucket 同款一项一许可信号量——回答"细粒度锁跳表是否比一把大锁还慢"。
**SkipList 数据为 #PERF-004 修复后**（删除全层级校验 + ThreadStatic 缓冲 + 内联 level-0 边，commit 89014d98）——修复前 2T 零吞吐的活性坍塌档案见 §4。

| 实现 | 1T ns/op | 2T ns/op | 4T ns/op | 8T ns/op | 8T 总吞吐 | 分配 B/op |
|------|---------:|---------:|---------:|---------:|----------:|----------:|
| Bucket | 151.6 | 232.4 | 193.0 | 231.4 | **34.6 Mops/s** | 48.7 |
| **LockedHeap（大锁+堆，对照）** | 304.5 | **154.0** | 231.1 | 250.4 | **32.0 Mops/s** | ~0 |
| Async（尾插修复后） | 466.7 | 615.2 | 539.9 | 635.7 | **12.6 Mops/s** | 1264 |
| SkipList（#PERF-004 修复后） | 465.6 | 465.3 | 657.5 | 851.1 | **9.4 Mops/s** | **92** |

### 解读（决定性数据）

- **Bucket 近线性扩展**（1T→8T 吞吐 ×5.2）：桶间天然分区，无队头热点。**多消费者 + 离散优先级 = 无脑选它**。
- **细粒度锁 vs 一把大锁（SkipList vs LockedHeap）——大锁领先 3.4×**：优先队列负载的 DeleteMin 全打
  队头、插入集中于少数优先级段——细粒度锁的"区间并行"收益趋零，lazy validate 失败重试是"做了功
  白做"，而大锁下每个操作线性推进零浪费。实测 8 线程 32.0 vs 9.4 Mops/s、单线程 305 vs 466ns。
  **吞吐优先的任意 long 场景，自建"一把 lock + 内置 PriorityQueue"仍是最优解**。
- **但 SkipList 修复后是健康可用的**（2T 与 1T 持平、8 线程 9.4 Mops/s、分配 92 B/op、MPMC 20 万项
  187ms）——不是修复前的"零吞吐活性坍塌"（§4 档案）。它的定位：任意 long + 中低并发 + 零分配
  路径 + 无锁 `TryPeek` 的**细分锁选项**，而非吞吐选择。
- **Async 并发下无锁优势兑现**：8 线程 12.6 Mops/s（ns/op 随线程数不升）。对照 LockedHeap 后定位清晰：
  Async 的价值不是吞吐（大锁更高），是**免疫持锁者延迟**（§5.2）——但 Workstation GC 下分配尾巴
  抵消此优势（§5）。

### 2.1 超额订阅扩展（16/32/64 线程 @ 12 逻辑核，Server GC——高核竞争的本地近似）

| 实现 | 8T Mops/s | 16T | 32T | 64T | 64T ns/op | 扩展形态 |
|------|----------:|----:|----:|----:|----------:|---------|
| Bucket | 37.6 | 72.4 | 148.2 | **292.8** | 219 | **完美线性**（ns/op 不涨） |
| LockedHeap | 37.7 | 66.1 | 135.0 | **245.0** | 261 | 近线性（大锁未饱和） |
| Async | 16.7 | 32.6 | 65.5 | **128.1** | 500 | 线性（ns/op 平） |
| SkipList | 11.0 | 20.5 | 30.2 | **46.4** | **1379** | **亚线性**（445→1379ns，3× 恶化） |

**解读与边界**：超额订阅下吞吐超过"核数 × 单线程"是流水线效应（跨线程 Enqueue/TryDequeue 重叠 +
时间片内批处理缓存热），不代表单核能力。**⚠️ 超额订阅 ≠ 真高核**：同核线程共享缓存，掩盖了真 64 核
下"64 个核抢一个锁字/CAS 目标的缓存行乒乓"——那才是大锁与队头单点结构的真正杀手，本机无法复现。
本表能下的结论：①扩展性分层是**分区（Bucket）> 大锁 > 队头单点 CAS（Async）> 队头锁链（SkipList）**；
②SkipList 的锁链在竞争压力下最先恶化（亚线性）；③**"无锁"属性本身不带来扩展性——热点是不是单点才带来**。

- 优先级分布偏斜（如 99% 同级）对 Bucket 更有利（扫桶命中第一桶）；对 Async 中性偏正（段内顺序追加）。

## 4. SkipList 活性坍塌档案——写法缺陷 #PERF-004 的发现与修复（已闭环）

> **状态：已修复**（commit 89014d98，2026-08-18）。本节保留取证档案——它同时是一次**误诊教训**：
> 压测首轮将活性坍塌归因为"锁版 DeleteMin 算法固有特征"（队头锁链热点 + validate 重试风暴），
> 实际根因是删除协议的层级校验缺失（写法 bug），算法本身没有问题。

### 4.1 根因（#PERF-004）

`TryDequeue` 的 validate **只校验 level-0**（`preds[0].Forward[0] != victim` 即重试）——高层 preds
陈旧时 `UnlinkVictim` 的守卫 `preds[i].Forward[i] == victim` 失手 → 该层不摘 → **被删除节点永久
滞留高层链** → Find 的 marked-skip 不在 key 处 break、每次扫完整条 marked 前缀 → **前缀持续增长**
（实测 2P+2C 涨至 2 万+）→ Find 从 O(log n) 退化 O(n) → 正反馈膨胀直至"零吞吐"。
修复：对齐 Herlihy 论文的全层级校验——标记即完整摘除，marked 节点永为瞬态。
配套：ThreadStatic 工作缓冲（每 op 4 数组分配 → 复用）+ Node 内联 level-0 边（省 ~50% 节点数组分配）
+ 锁外收尾（计数/唤醒不占 pred 自旋锁）+ maxLevel 构造护栏（2^maxLevel ≥ 预期条目数，层级不足
同样 O(n) 退化）。

### 4.2 修复前后对照（同机同负载）

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 混合往返 2T | 探测轮 10s **零吞吐**（0/100K ops，CPU 烧数千秒） | **465ns（4.3 Mops/s）**，与 1T 持平 |
| 混合往返 8T | 护栏跳过 | 851ns（**9.4 Mops/s**） |
| MPMC 4P+4C × 20 万项 | 53.7s（波动 3.7~57s） | **187 ms（287×）** |
| MPSC / DequeueAsync | 45s/30s 活性失败 | 全收齐 ✓（正确性 16/16） |
| think-time 负载 | 30s 进度停滞坍塌 | **135,151 ops/s**（max 15.5ms，优于 Async） |
| 分配 | 1384 B/op | **92 B/op** |

### 4.3 修复后仍成立的结构性结论

细粒度锁 vs 一把大锁的相对关系**没有变**（只是差距从 ∞× 修正为 3~4×）：优先队列负载的
DeleteMin 全打队头、插入集中于少数优先级段——区间并行的收益趋零，validate 失败重试仍是
"做了功白做"。实测 8 线程 LockedHeap 32.0 vs SkipList 9.4 Mops/s、单线程 305 vs 466ns。
**吞吐优先的任意 long 场景大锁仍是首选**；SkipList 修复后的定位：任意 long + 中低并发 +
零分配路径 + 无锁 `TryPeek` 的细分锁选项。

### 4.4 取证与误诊记录（方法论存档）

- dotnet-stack：线程卡 `Enqueue`/`TryDequeue` 内部烧 CPU——**当时误读为"锁竞争重试风暴"**，
  实际是在 Find 里线性扫描 marked 前缀；
- 锁序分析（Enqueue/Dequeue 均 key 降序加锁、无环）正确排除了死锁，但"活锁/算法固有"的归因
  停在了症状层——**没追问"为什么 validate 失败率这么高、CPU 在扫什么"**；
- 教训：**"零吞吐 + CPU 全速燃烧"更像结构退化（每次 op 变贵）而非锁竞争（每次 op 等锁）**——
  前者随时间恶化且单线程也会露出马脚（积压敏感性实验里 SkipList A 负载 64K/256K 的 1.2/0.9µs
  已是前缀膨胀的前兆，当时被当作"跳表 log 增长"放过了）。

## 5. 真实负载维度——think-time 与持锁者延迟（2026-08-17 补测）

> §2/§3 的吞吐矩阵是"背靠背纯内存操作"微基准：临界区 50ns 且从不被外部延迟——**偏向大锁**
> （持锁者被抢占/GC 暂停的窗口 ≈ 万分之一）。本节补测两个真实维度，回应"纯吞吐对比不完整"：
> 负载 A（think-time）：worker 出队→干活（随机长耗时）→回来；负载 B（毒丸）：持锁线程被外部延迟。

### 5.1 think-time 负载（8 线程，往返间自旋指数分布均值 50µs——模拟出队→干活→回来）

| 实现 | 总吞吐 ops/s | op p50 | op p99 | op p999 | op max |
|------|-------------:|-------:|-------:|--------:|-------:|
| Bucket | 144,724 | 300 ns | 1.3 µs | 5.4 µs | 6,408 µs |
| LockedHeap（大锁+堆） | 143,366 | **200 ns** | 800 ns | 2.0 µs | **606 µs** |
| SkipList（#PERF-004 修复后） | 135,151 | 700 ns | 2.7 µs | 17.7 µs | 15,478 µs |
| Async | 130,029 | 600 ns | 3.2 µs | 53.6 µs | 21,900 µs |

**解读**：
- **think-time 下大锁并不溃败**——队列操作占比 <2% 时锁几乎无竞争，LockedHeap 与 Bucket 完全同级
  （吞吐 143K vs 145K ops/s，LockedHeap 的 p50/max 甚至全场最优）。§2"大锁吞吐王"的结论
  **延伸到低频真实负载依然成立**。
- **SkipList 修复后 think-time 负载健康**（135K ops/s，与 Async 同级）——修复前此负载 30s 进度
  停滞坍塌（§4 档案）。
- **Async 的尾延迟被自身分配压力拖累**（p999 53.6µs、max 21.9ms）：1.3 KB/op 的 Gen0 分配率在
  Workstation GC 下制造毫秒级 GC 停顿——**无锁 ≠ 低尾延迟，分配率才是尾延迟杀手**。

### 5.2 持锁者毒丸（8 线程高频往返，0.2% 操作注入 2ms 延迟）

注入位置的结构差异就是被测对象的结构差异：**LockedHeap☠ 把 2ms 注入在锁内**（模拟持锁线程被
抢占/GC 暂停/页错误），其余实现注入在操作前（延迟只属于自己）。报告**非毒丸** op 的延迟分布——
"一个人的延迟变成全队的灾难"的直接量化：

| 实现 | 注入位置 | 非毒丸 p50 | p99 | p999 | max | max/p50 |
|------|---------|-----------:|----:|-----:|----:|--------:|
| Bucket | 操作前 | 500 ns | 3.8 µs | 10.6 µs | 309 µs | 617× |
| LockedHeap | 操作前（对照） | 700 ns | 6.8 µs | 48 µs | 1,500 µs | 2,143× |
| **LockedHeap☠** | **锁内** | 700 ns | 8.3 µs | **46.6 ms** | **140.6 ms** | 200,905× |
| Async | 操作前 | 1.3 µs | 6.4 µs | 206 µs | 186 ms | 143,224× |

**解读（本节最重要的一组数字）**：
- **大锁柱塞实锤且被放大 ~70 倍**：同样 0.2% × 2ms 的延迟剂量，锁外注入时 max 1.5ms（正常长尾），
  **锁内注入时非毒丸 op 的 p999=46.6ms、max=140.6ms——max 放大 94 倍**。机理：持锁者延迟期间
  全队积压在锁上，恢复后 burst 冲锁 → 唤醒风暴 → 雪崩。**真实系统里持锁线程被 OS 抢占、GC 暂停、
  页错误是常态**——大锁的吞吐王座有明确的适用条件：临界区短 **且** 持锁者不被外部长时间延迟。
- **Async 对持锁者延迟结构性免疫**（别人 2ms 的延迟不会通过任何锁传播给自己——它的毒丸分布
  与普通负载一致），**但它的 GC 尾巴（186ms max）比柱塞本身还大**——在 Workstation GC + 高分配
  下，无锁的柱塞免疫被分配停顿抵消。Server GC / 降分配（B' 路线）才能兑现无锁的延迟确定性。
- Bucket 全维度最稳：无单点锁、无大分配（48B/op 摊销）——毒丸下 max 仅 309µs。

### 5.3 Server GC 对照（DOTNET_gcServer=1，2026-08-18 补测——回应"高核 + GC 调整后算法才有价值"）

| 指标（8 线程） | Workstation GC | Server GC | 变化 |
|---|---:|---:|---|
| Async 吞吐 | 12.6 Mops/s | **17.4** | **+38%**（并行回收释放分配压力） |
| LockedHeap 吞吐 | 32.0 | 37.5 | +17% |
| Bucket think-time max | 6,408 µs | **109 µs** | **59×** |
| SkipList think-time max | 15,478 µs | **205 µs** | **75×** |
| LockedHeap think-time max | 606 µs | 343 µs | 1.8× |
| **Async think-time max** | 21,900 µs | **30,855 µs** | **反而最差** |
| **Async 毒丸非毒丸 max** | 170 ms | **248~326 ms** | **依然全场最差** |
| SkipList 毒丸非毒丸 max（首次参与） | — | 62 ms | 比 LockedHeap（1.3ms）差 47× |

**结论**：GC 调整确实释放了大部分实现的尾延迟（Bucket/SkipList 改善 59~75×）——但
**Async 是例外**：1.3 KB/op 的分配率连 Server GC 的并行回收都打不服（think-time/毒丸 max
依然 31ms/250ms+，比它免疫掉的柱塞还大一个数量级）。Async 兑现"无锁延迟确定性"的前提
不是 Server GC，是**降分配**（B' 零分配路线）。SkipList 的毒丸数据（62ms）说明分段锁只
**部分免疫**持锁者延迟——victim+preds 链上的锁被延迟者持有时照样传导。

## 6. 并发正确性压测（Debug 链校验器 + Release 全量）

**方法论**：P=4 生产者各 N 唯一项（均匀 0..7）× C 消费者尽力消费 → 超时停止 → 主线程单线程 drain 收尾
（drain 段无竞态、序断言 100% 可靠）→ 全集 HashSet 校验。Debug 构建下 AsyncPriorityQueue 每 64 op
自动巡检链不变式（key 严格递增 / marker 链长 ≤1 / 步数护栏）。

| 场景 | Bucket | SkipList | Async（修复后） | LockedHeap（对照） |
|------|--------|----------|-----------------|--------------------|
| MPMC 不丢不重（40 万项 Debug / 20 万项 Release） | ✓ | ✓（187ms，#PERF-004 修复后） | ✓ | ✓ |
| SPSC 严格序（生产先行，消费段 0 反转硬断言） | ✓ | ✓ | ✓ | ✓ |
| MPSC 排序语义（drain 0 反转 + 全序列反转率参考） | ✓ 25.2%¹ | ✓ 18.0%¹ | ✓ 8.9%¹ | ✓ 10.0%¹ |
| DequeueAsync 等待-唤醒（4 消费者先真实挂起再生产） | ✓ | ✓（修复后全收齐——修复前 30s 活性失败，§4） | ✓ | ✓ |
| DEBUG 链校验器（巡检 6 千+ 次/场景） | —（无此仪器） | —（无此仪器） | ✓ 无结构损坏 | —（一把锁无从损坏） |

¹ 反转率是"竞争性最小"语义的固有参考值（后到的更高优先级项可越过已出队的低优先级项），非缺陷；
单消费者语义下（SPSC 硬断言）三者全部 0 反转。

## 8. 选型速查（全部为实测数据支撑）

| 场景 | 选择 | 依据 |
|------|------|------|
| 优先级 = 少量离散枚举（4~16 级） | **Bucket** | 单线程 52ns、8 线程 34.6 Mops/s、think-time/毒丸全负载最稳（§5）——**没有短板的全维度王** |
| 优先级任意取值 + 高吞吐 + 临界区短且持锁者不被外部长延迟 | **自建一把 lock + 内置 `PriorityQueue`**（LockedHeap 模式） | 8 线程 32.0 Mops/s、单线程 305ns、think-time 下 p50/max 全场最优（§5.1）。⚠️ **柱塞边界（§5.2）**：持锁者被抢占/GC/页错误时全队 max 放大数百倍——延迟敏感场景换 Bucket/Async |
| 任意 int 优先级 + 免疫持锁者延迟（无单点锁依赖） | **Async** | 8 线程 12.6 Mops/s、256K 积压 1.3µs、别人的延迟不通过锁传播。⚠️ 分配率 1.3KB/op 在 Workstation GC 下尾延迟 22~170ms（§5）——延迟敏感需 Server GC 或 B' 零分配路线 |
| 任意 long 优先级 + 中低并发 / 零分配路径 / 无锁 `TryPeek` | **SkipList**（#PERF-004 修复后） | 单线程 466ns、8 线程 9.4 Mops/s、分配 92 B/op、think-time 135K ops/s（§4.2）——健康可用的细分锁选项；吞吐落后大锁 3~4×（§2），吞吐优先选大锁 |
| 单线程/无并发 | .NET 内置 | 11ns——线程安全的定价不值 |

## 9. 已知边界

- Windows Workstation GC 实测；Server GC / Linux 下 Async 分配压力（1.3 KB/op）的 GC 频率未单测。
- 探针吞吐用 Thread 直起（非 ThreadPool），与真实异步工作负载的调度差异未消除——数据用于**实现间横向对比**。
- §5.1 think-time 用自旋模拟计算型 worker（均值 50µs 指数分布）；IO 型 worker（Sleep 让出）未测。
- §5.2 毒丸剂量 0.2% × 2ms 为单一组合；柱塞放大系数随剂量/线程数变化，未做扫参——且为 #PERF-004
  修复前跑的（SkipList 未参与，探针已放行、下轮补数）。
- short job 快速基线；正式入库用默认 job 复跑。
